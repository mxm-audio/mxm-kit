# Decoder fixtures

**Our own work.** Every file here but `tone.caf` was rendered from one synthesised signal — a
linear sweep from 200 to 2,200 Hz at 0.5 on the left and from 3,000 down to 1,500 Hz at 0.3 on the
right, 44.1 kHz, half a second (three, for `tone-3s.ogg`) — generated by ffmpeg's `aevalsrc` from the formula below. `tone.caf`
is a 0.02 s sine from its own line below: it exists only to be refused. The `tone.*` names predate
the sweep.

**A sweep, not a tone, and on purpose.** The first set used steady 440 and 660 Hz sines, and the
offset measurement found a "lag" of 2,205 frames at a correlation of 1.000000: exactly 22 periods of
440 Hz. A periodic signal matches itself one period over, so it cannot measure where audio starts.
A sweep has one alignment. No recording, sample library or third-party audio is involved.
The root release checklist's media check (item 1; since the split, *Before this repository is made
public* in mxm-kit's [`docs/collection-rules.md`](../../../docs/collection-rules.md#research-boundary))
finds these files; this README and `../AGENTS.md` are the declaration it asks for.

They exist because no Rust crate the collection uses can **write** MP3, AAC, ALAC, Vorbis or Opus.
WAV, AIFF and FLAC are written by `mxm-audio-file` inside the tests instead.

Made with ffmpeg 8.1.1 (full build: libmp3lame, native aac and alac, libvorbis, libopus), from
this folder:

```sh
COMMON='-hide_banner -v error -y -fflags +bitexact -flags:a +bitexact'
SRC='aevalsrc=0.5*sin(2*PI*(200*t+2000*t*t))|0.3*sin(2*PI*(3000*t-1500*t*t)):s=44100:d=0.5'

ffmpeg $COMMON -f lavfi -i "$SRC" -c:a pcm_s16le reference-s16.wav
ffmpeg $COMMON -i reference-s16.wav -c:a alac tone-alac.m4a
ffmpeg $COMMON -i reference-s16.wav -c:a libmp3lame -b:a 128k -id3v2_version 3 -metadata title=mxm-fixture tone.mp3
ffmpeg $COMMON -i reference-s16.wav -c:a libmp3lame -b:a 128k -write_xing 0 tone-untagged.mp3
ffmpeg $COMMON -i reference-s16.wav -c:a aac -b:a 128k tone-aac.m4a
ffmpeg $COMMON -i reference-s16.wav -c:a libvorbis -q:a 4 tone.ogg
ffmpeg $COMMON -f lavfi -i "${SRC%:d=0.5}:d=3" -c:a libvorbis -q:a 4 tone-3s.ogg
ffmpeg $COMMON -i tone-3s.ogg -c copy -output_ts_offset 2 tone-3s-offset.ogg
ffmpeg $COMMON -ss 1 -i tone-3s.ogg -c copy tone-3s-cut.ogg
ffmpeg $COMMON -i reference-s16.wav -c:a libopus -b:a 64k tone.opus
ffmpeg $COMMON -f lavfi -i "aevalsrc=0.5*sin(2*PI*440*t):s=44100:d=0.02" -c:a pcm_s16le tone.caf
```

| File | Why it is here |
|---|---|
| `reference-s16.wav` | The 16-bit samples every other file was encoded from |
| `tone-alac.m4a` | ALAC in ISO/MP4 — must decode to the reference exactly |
| `tone.mp3` | MP3 with an ID3v2.3 tag in front — gapless, zero offset, and probed past the tag |
| `tone-untagged.mp3` | The same MP3 without its Xing/LAME header — no declared delay, so not gapless: the priming stays in. **CBR on purpose**: an untagged VBR file is shortened by symphonia's length estimate, which would confound this test |
| `tone-aac.m4a` | AAC-LC in ISO/MP4 — decodes, and reports itself not gapless |
| `tone.ogg` | Vorbis in Ogg — gapless, zero offset |
| `tone-3s.ogg` | The same formula for three seconds, encoded from the formula rather than the reference WAV: five pages, so an audio page can be lost from the middle or before the end — refused either way |
| `tone-3s-offset.ogg` | `tone-3s.ogg`'s packets with every timestamp moved 2 s later: starts at 88,072, ends at granule 220,500, and is still 132,300 frames |
| `tone-3s-cut.ogg` | `tone-3s.ogg`'s packets re-timed by a `-ss 1` copy: starts at −44,228, ends at 88,200, and is still 132,300 frames |
| `tone.opus` | Opus in Ogg — refused as an unsupported codec (owner ruling, 2026-09-15) |
| `tone.caf` | CAF — refused as not audio, because symphonia rates its CAF reader Good ("may panic") |

The ALAC and lossy files are encoded from `reference-s16.wav`, not from the formula, so the ALAC file
holds exactly its samples. Re-encoding with a different ffmpeg may change lossy bytes; the tests
compare lossy audio by alignment and correlation, never exactly.
